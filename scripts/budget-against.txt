# What the comparisons against other people's libraries may spend.
#
# Same format and same gate as scripts/budget.txt, for the benchmarks that live
# in their own module under benchmarks/ so that the module everybody builds
# keeps its one direct dependency. Run with `make bench-against`.
#
# Measured on go1.27 for a 64-bit word.

# Validation, against go-playground/validator over the same subject with the
# same rules written both ways.
#
# The allocation figures are the durable half: the generated check allocates
# nothing, the reflective one six times. Where those six come from is not
# reflection, which is worth writing down because it is the obvious guess.
# Walking the fields reflectively allocates nothing at all. One allocation is
# the subject copied into the `any` go-playground's entry point takes, and the
# other five are inside its `email` rule, which parses the address with
# net/mail before matching its own pattern.
#
# So most of the difference is what the two rules ask for rather than how
# either check was built, and that is not a gap the benchmark can close. The
# subject asks for a pattern; go-playground has no pattern rule, and says so
# deliberately — commas and equals signs can appear in a regex and would
# collide with its own tag syntax, so it asks for a registered function
# instead. `email` is the nearest thing in its vocabulary, and it does more
# work than the pattern does.
#
# Read the speed multiple in that light and do not read much into it: it moves
# with the run length, so it is a figure for the machine it was measured on.
# The memory claim is the one that travels. See the note beside twin in
# validator_test.go for the field where the two rules part company.
